# Operational observability v1 — prepared, not activated

This is a source-only foundation. Production persistence is **disabled by default**. Do not set `OPEN_ORDER_OPS_ENABLED=1` or apply `operational-schema-review.sql` until the operator approves the separate production schema/role/scheduler plan, has tested it in an isolated database, verifies provider retention and access controls, and publishes the corresponding notice. No current production schema or credentials change in this release. The historical raw-query writer remains removed; the live legacy table was emptied through a separate authorised transaction. Backups and restore procedures still require review.

## Contract

One bounded metadata event per ordinary search POST and per AI stream that reaches its existing stream start. Search counts returned results, not unique users; outcome reflects HTTP response status. AI outcome reports whether the server attempted a terminal done/error event (not a semantic answer-quality verdict or proof of delivery); stage count and last known stage reflect the existing stage timeline, not detailed diagnostics. Unknown stage names become `other`. AI early validation responses and legacy GETs are not persisted. Request reference is random, not a user or session ID. Release SHA is a server build identifier; absence prevents writing. No query, prompt, answer, source IDs, provider payload, free-form stage label, headers, URL, IP, session, token or hash of user content is accepted. Existing in-session diagnostics remain unchanged. There is no new public lookup API. This initial schema omits provider/model, corpus version, fine-grained stage durations, retry/validation counts and longer-lived aggregate storage pending demonstrated need. Metrics may be derived from the short-lived reader view without introducing a second datastore. Do not infer unique users or publish small sensitive cells.

## Activation gates (not performed by source release)

- Create separate owner, writer, reader and purger roles on an isolated test database first. Owner is NOLOGIN; writer/purger are distinct restricted LOGINs; only authorised maintainer can assume reader; no inherited corpus/admin privileges. Verify role memberships, schema privileges, function execution grants and database identity. Do not use the existing corpus credential for writer/purger. Review SQL against the actual PostgreSQL version and permissions before applying; the file is deliberately outside the normal migration directory.
- Test write success, invalid DTO/SQL rejection, writer cannot read/delete, purger cannot read/write, reader sees only active traces, expired rows are physically removed, purge failures/backlog stop new inserts, no public grants, rollback/disable and restore safeguards. Seed only synthetic fixtures. Verify connection TLS and application behaviour when writer disabled/unavailable.
- Provision an independently monitored hourly scheduler using the purge-only credential. Each invocation calls `select open_order_ops.purge_expired_v1()` in a bounded transaction with a statement timeout. It returns a count, no rows. Repeat bounded batches if required. Alert on missed runs, failures, backlog and stale heartbeat. The database refuses new writes without a successful purge within two hours. The reader view excludes records aged 14 days; physical expiry is targeted at 14 days plus scheduling delay. A failed scheduler cannot erase existing data automatically: stop collection and remediate; review backup/PITR lifecycle. Do not claim hard physical deletion at 14 days unless verified. Do not enable if scheduler/alerts/access cannot be enforced.
- Publish truthful privacy notice before enabling. Set only the separate production connection secret `OPEN_ORDER_OPERATIONAL_DATABASE_URL` and explicit `OPEN_ORDER_OPS_ENABLED=1`; verify runtime uses writer role and exact deployment SHA. Verify positive synthetic events, no content, no legacy rows, and failure isolation. Revoke/disable writer if rollback needed; never restore a raw-query-writing release. Credential values must not appear in reports.

Writer failure is isolated by Next.js after-response scheduling and bounded pool/query timeouts; a saturating per-instance failure counter is maintained without logging exception data. It is not a durable monitor or guaranteed delivery; platform termination can lose traces. Scheduler monitoring and a private operator read workflow are required before activation. No durable traces, aggregate store, volunteered diagnostic or abuse datastore are enabled in this source release.
